# 6. Соответствие 12 принципам разработки агентов

[К оглавлению HLD](../customer-support-agent-hld.md)

Основа — [12-Factor Agents, HumanLayer](https://github.com/humanlayer/12-factor-agents). Ниже сохранены исходные номера; четыре группы и решения для поп-ап чата — адаптация к нашему проекту. Это руководство по проектированию, а не требование использовать конкретный фреймворк. Новых каналов общения и отдельных микросервисов эти принципы сами по себе не требуют.

## 6.1. Понимание запроса и решение

| № / принцип | Решение в HLD | Как проверить |
| --- | --- | --- |
| 1. [Естественный язык → вызовы инструментов](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-01-natural-language-to-tool-calls.md) | Узкая задача переводит запрос в типизированное предложение: поиск, уточнение, подготовка действия, передача. Сервер отдельно принимает решение об исполнении | На эталонных запросах выбран корректный тип и аргументы; неоднозначность приводит к уточнению |
| 2. [Управление промптами](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-02-own-your-prompts.md) | Версионируемые инструкции и контракты; версия фиксируется в шаге, изменение проходит регрессионную оценку и допускает откат | Для ответа можно установить использованные инструкции; изменение не ухудшает согласованные сценарии |
| 3. [Управление контекстным окном](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-03-own-your-context-window.md) | Сборщик отбирает доступные историю, резюме, источники и результаты в заданном бюджете; актуальные статусы читаются через API | Длинная история не переполняет контекст; чужие данные исключены; устаревший ответ не подменяет текущий статус |

Связанные разделы: [принятие решения и состав контекста](01-components.md#213-принятие-решения), [ответ по FAQ](03-scenarios.md#42-faq-с-учётом-истории). Схемы: [01](../../images/01-components.svg), [06](../../images/06-faq-context.svg).

## 6.2. Исполнение и состояние

| № / принцип | Решение в HLD | Как проверить |
| --- | --- | --- |
| 4. [Инструменты — структурированный выход](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-04-tools-are-structured-outputs.md) | Предложение LLM проходит проверку схемы, разрешённых операций, прав и согласия; у LLM нет прямых учётных данных бизнес-систем | Некорректный выход или неизвестный инструмент не вызывает внешний эффект |
| 5. [Согласование состояния исполнения и процесса](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-05-unify-execution-state.md) | Общая модель Conversation, AgentRun, операции и журнала; атомарное сохранение перехода и outbox | Ожидание согласия всегда связано с конкретным предложением; после сбоя нет состояния без соответствующей команды / события |
| 6. [Запуск, пауза и продолжение через API](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-06-launch-pause-resume.md) | Явные контракты запуска, чтения статуса, отмены и продолжения. Ожидания сохраняются, продолжение принимает только соответствующее событие | Перезапуск и закрытие браузера не теряют ожидание; чужое или просроченное подтверждение его не продолжает |

Принцип №5 не означает единую физическую БД для всех систем. Заказ остаётся в системе заказов; внутренняя модель агента хранит ссылку и наблюдавшийся результат. Принцип №4 уточняет границу ответственности, а №1 — назначение преобразования запроса.

Связанные разделы: [контролируемые возможности](01-components.md#214-контролируемые-возможности), [состояние и жизненный цикл](02-state-lifecycle.md). Схемы: [02](../../images/02-action-consent.svg), [04](../../images/04-state-model.svg), [05](../../images/05-run-lifecycle.svg).

## 6.3. Люди, управление потоком и ошибки

| № / принцип | Решение в HLD | Как проверить |
| --- | --- | --- |
| 7. [Обращение к людям через инструменты](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-07-contact-humans-with-tools.md) | Уточнение, согласие клиента и передача оператору — разные типизированные шаги со своим ожиданием и ответом | Подтверждение карточки не воспринимается как принятие оператором; оператор получает достаточный контекст |
| 8. [Управление потоком выполнения](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-08-own-your-control-flow.md) | Оркестратор проверяет переходы, бюджеты, остановку, владельца и допустимость повтора; обязательная передача не зависит от LLM | Лимит завершает цикл; без согласия нет исполнения; после принятия оператором автономные ответы прекращаются |
| 9. [Ошибки в контексте](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-09-compact-errors.md) | Нормализованный сбой передаётся в контекст без секретов; сервер ограничивает последующее действие. Неизвестный результат отделён от подтверждённой ошибки | Модель может выбрать уточнение / эскалацию; тайм-аут не запускает слепой повтор потенциально выполненной операции |

Связанные разделы: [сценарии](03-scenarios.md), [ошибки и ограничения](05-quality-security.md#52-обработка-ошибок-и-ограничения). Схемы: [02](../../images/02-action-consent.svg), [05](../../images/05-run-lifecycle.svg), [07](../../images/07-human-handoff.svg).

## 6.4. Ограничение сложности и восстановление

| № / принцип | Решение в HLD | Как проверить |
| --- | --- | --- |
| 10. [Узкие агенты](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-10-small-focused-agents.md) | Ограниченные задачи ответа, подготовки действия и эскалации с отдельным контекстом, контрактом и бюджетом; допустимы модули одного приложения | Каждая задача проверяется отдельно и не получает ненужные инструменты / права |
| 11. [Разные источники запуска, привычный канал клиента](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-11-trigger-from-anywhere.md) | Клиент работает в поп-апе; подтверждения, результаты API и события оператора продолжают процесс независимо от открытой вкладки | Результат сохраняется без браузера и доступен после открытия; новые каналы не нужны для текущего объёма |
| 12. [Stateless reducer](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-12-stateless-reducer.md) | Шаг получает явно загруженное состояние и событие; решение и команды сохраняются до внешнего эффекта. Нет необходимой скрытой памяти обработчика | Другой обработчик продолжает задачу по сохранённому состоянию; повтор зафиксированного события не исполняет действие заново |

Для №12 это рабочая архитектурная трактовка: в первоисточнике раздел краток. Она не обещает детерминированность LLM или исполнение внешнего API «ровно один раз». Эти риски отдельно закрывают журнал, проверка версии, outbox, идемпотентность и сверка результата.

Связанные разделы: [обработка шага](02-state-lifecycle.md#32-общая-модель-обработки), [восстановление](03-scenarios.md#45-восстановление-после-разрыва-связи-или-перезапуска). Схемы: [01](../../images/01-components.svg), [04](../../images/04-state-model.svg), [08](../../images/08-recovery.svg).
